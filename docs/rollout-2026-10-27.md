## Resulting product behavior

- Home `recommended`: active verification first, GitHub stars descending, then
  project ID descending. Category/tag/license catalogues default to Most stars;
  explicit Latest remains chronological. No billing or editorial homepage scope.
- Project representatives can inspect members and leave, including hidden
  listings. Another current admin can change a project role or revoke another
  account. Last-active-member removal drops verification and restores admin
  bootstrap review; return requires fresh proof and independent approval.
- Admins can search/filter users, inspect safe account/session/provider summaries,
  assign account `user`/`admin`, ban/unban and revoke all sessions. Project roles
  remain scoped separately. Self-ban, last-active-admin loss, stale actions and
  native admin-write bypasses are guarded.
- `/admin`, `/admin/submissions` and `/admin/ownership` lead to existing review
  flows. `/admin/activity` reads safe recorded audit fields with URL filters;
  `/admin/operations` reads GitHub snapshot and review-outbox observations.
  Scheduler/failure telemetry is unavailable; Sent means provider acceptance.
  These observations do not establish historical analytics or backup health.

running revisions before deciding which steps remain. The 27-entry recovery
snapshot is historical and does not prove the current 28-migration source state.

   `vp run --filter @altstack/db db:validate-audit-actions` against the **same

   ordinary reads/writes. Record the journal and validated constraint outcome.
4. Publish and deploy a matching immutable API/Web revision pair. The repository's
   [Docker workflow](../.github/workflows/publish-docker.yml) runs on `v*` tags or
   explicit workflow dispatch; merging this PR alone does not publish images.
   Record the selected tag/revision, OCI labels and actual running revisions.
5. Preserve trusted origins/proxy/cookie settings, GitHub/Resend configuration,
   existing 02:00 WIB GitHub and every-minute review-email jobs, and temporary
   media lifecycle. No extra dashboard job, service or secret is required.
6. Run focused target acceptance below and record results and skipped cases.
   On failure, retain additive migrations and the journal; use the previous
